ADMINISTRATION RÉSEAU : PRINCIPES ET SUPERVISION

1. PRINCIPES GÉNÉRAUX - LES CINQ AXES ISO
- Gestion des anomalies (Fault Management) : réseau opérationnel sans rupture de service (99,999 % de disponibilité = quelques secondes d'indisponibilité par an, ce qui définit une QoS). Localiser rapidement toute panne : surveiller les alarmes, localiser un incident par diagnostic des alarmes, journaliser les problèmes.
- Gestion de la configuration (Configuration Management) : gérer la configuration matérielle et logicielle pour optimiser l'utilisation ; chaque équipement et compteur identifié de façon unique par un nom ou un identificateur d'objet OID (Object Identifier).
- Gestion des performances (Performance Management) : contrôler à tout moment si le réseau écoule le trafic pour lequel il a été conçu.
- Gestion de la sécurité (Security Management) : contrôles d'accès au réseau, confidentialité, intégrité et authentification des données.
- Gestion de la comptabilité (Accounting Management) : suivre la consommation réseau par abonné pour établir une facture.
Enjeux : offrir une solution unique pour administrer un milieu hétérogène, avec des outils adaptables à la taille et à la diversité technologique ; automatiser le traitement de l'information pour agir « pro-activement » et non « réagir en mode pompier ». Superviser = anticiper, prévoir, éviter de subir.

2. ASPECTS ORGANISATIONNELS
Deux écueils à éviter : l'absence (ou l'insuffisance) d'informations ; le trop-plein d'informations (« trop d'informations tue l'information »), qui survient quand les aspects organisationnels n'ont pas été suffisamment pris en compte.
Étapes préparatoires : plan du réseau (diagrammes, schémas) ; plan d'adressage ; recensement des pratiques des utilisateurs (développeurs, exploitants et techniciens, utilisateurs finaux) ; détermination des équipements actifs à prendre en charge (approche séquentielle calquée sur la modélisation en couches) ; détermination des objets et services par équipement ; regroupement en entités logiques (politique de supervision par groupe d'objet, interactions entre objets, seuils d'alertes et groupes à alerter) ; politiques par type de service (seuils, cas particuliers) ; choix des outils. S'appuyer sur la modélisation en couches ; prendre en compte la globalité des composants (pas seulement les couches 2-3 du modèle DOD).
Trois catégories d'objets à superviser :
- Supervision réseau : communication entre machines ; bon fonctionnement des communications et performance des liens (débit, latence, taux d'erreurs) ; ex. vérifier qu'une IP est joignable, qu'un port est ouvert.
- Supervision système : la machine elle-même et ses ressources (mémoire utilisée, charge processeur, logs système).
- Supervision applicative : fonctionnement d'une application ; connexion sur son port pour vérifier qu'elle retourne les bonnes informations, analyse de logs applicatifs. Un port ouvert ne garantit pas que l'application derrière n'est pas « plantée ».

3. ASPECTS PROTOCOLAIRES
ICMP (Internet Control Message Protocol) : protocole de couche 3 (réseau) qui palie l'absence de message d'erreur d'IP ; les équipements intermédiaires l'utilisent pour prévenir la machine émettrice d'un incident. Paquets ICMP encapsulés dans des paquets IP, pouvant contenir des bouts du paquet IP fautif. Erreurs classées en types, parfois re-divisés en codes (type 3 = destinataire inaccessible, 16 codes). Simple ; pas de fonction directe de supervision, mais source d'information (qualité du réseau, présence d'un hôte).
SNMP (Simple Network Management Protocol) :
- Contexte : l'ISO a proposé dans les années 80 la norme CMIS/CMIP (Common Management Information Service ISO 9595, Common Management Information Protocol ISO 9596) et un cadre architectural (ISO 7498). En parallèle, l'IAB (Internet Activities Board) a approuvé SNMP comme solution à court terme et CMOT (CMIP Over TCP) à long terme. Au début des années 90, SNMP, plus simple, est devenu le standard de fait, adopté par de nombreux constructeurs (réseaux IP et réseaux d'opérateurs comme ATM). SNMP a repris et adapté beaucoup des idées de CMIS/CMIP.
- Trois éléments : base de données MIB gérée par chaque agent, modifiable par un manager (RFC 1156 et 1213 pour la MIB-I puis la MIB-II) ; structure commune de représentation SMI (Structure of Management Information, RFC 1155) ; protocole d'échange SNMP entre manager et agent (RFC 1157).
- Bâti au-dessus d'UDP/IP : UDP pour sa simplicité, sa rapidité et sa concision (8 octets d'en-tête contre 20 pour TCP) -> remontée rapide des alarmes ; mais non connecté et non fiable -> perte de messages possible.
- Cinq types de messages SNMPv1 : get-request (GET, valeur courante d'un objet), get-next-request (GETNEXT, prochain objet), set-request (SET, mise à jour d'une valeur), get-response (réponse à GET/GETNEXT/SET), trap (TRAP, signal d'un agent vers un manager, remontée d'alarme). Protocole commande/réponse sans états.
- Ports UDP : 161 côté agent (GET, GETNEXT, SET) ; 162 côté manager (TRAPs).
- Champ communauté (community) : chaîne de caractères = mot de passe de validation ; si incorrecte, requête rejetée ; passe en clair -> faille importante de SNMPv1, comblée par les versions ultérieures.
- Encodage TLV (Type, Longueur, Valeur) / BER (Basic Encoding Rules) défini dans la SMI ; gourmand en octets (un octet -> trois octets) ; nombre variable de paramètres.
- SMI : règles de description ; identifie de façon unique un objet de la MIB (OID, Object ID) ; représentation des données et types ; objet déclaré/défini en ASN.1 (Abstract Syntax Notation 1). Types utilisés : INTEGER (32 bits complément à 2), OCTET STRING, IpAddress, PhysAddress (MAC 6 octets), Counter (entier 32 bits non signé, retour à 0 après 2^32-1), TimeTicks (compteur 32 bits non signé en 1/100 de s).
- MIB : base de données de l'agent, structure d'arbre similaire au DNS ; racine non nommée ; objet identifié de façon absolue par son OID (nœud de l'arbre) ; chaque nœud a aussi un nom symbolique. Ex. sysDescr = iso.org.dod.internet.mgmt.mib.system.sysDescr.0, OID = 1.3.6.1.2.1.1.1.0. Les objets utiles commencent par 1.3.6.1.2.1. C'est l'OID qui est transmis dans une requête, pas le nom symbolique. MIB standard vs MIB privée (objets propres, branche iso.org.dod.internet.private.enterprises.nom_entreprise ; souscrire un numéro d'entreprise à l'IANA). Accès à un objet simple (feuille) : ajouter .0 en suffixe à l'OID.
- Versions : SNMPv1 (RFC 1155, sécurité triviale par la chaîne « community ») ; SNMPsec (historique, sécurité par groupes, oublié) ; SNMPv2p (mise à jour des opérations, nouveaux types, sécurité par groupes) ; SNMPv2c (community string-based, RFC 1441) ; SNMPv2u (sécurité basée sur les usagers) ; SNMPv2* (combine v2p et v2u, jamais publié en RFC, RFC 1901) ; SNMPv3 (standard actuel, RFC 3411 ; sécurité basée sur les usagers + types/opérations de SNMPv2p + capacité pour les proxies).
NET-SNMP : implémentation libre sous Linux. Ensemble d'outils : API d'accès à SNMP, agent SNMP extensible, commandes en ligne pour interroger des agents et gérer/générer des TRAPs, version de netstat utilisant SNMP, browser de MIB (tkmib) écrit en Tk. Porté sur Linux, HP-UX, Solaris, SunOS, NetBSD, FreeBSD, Win32. Supporte SNMPv1/v2/v3.
- Agent : exécutable snmpd ; fichier de configuration snmpd.conf (exemple EXAMPLE.conf) ; utilitaire snmpconf pour le créer interactivement (snmpconf -g basic_setup).
- Commandes : snmpget (GET), snmpset (SET), snmpgetnext (GETNEXT + valeur de l'objet suivant), snmpwalk (balaye complètement une branche de la MIB), snmptranslate (OID décimal <-> forme symbolique).

4. OUTILS DE SUPERVISION
« Petits » outils (briques de base) :
- Ping : utilise ICMP (requête Echo, réponse Echo Reply) ; savoir si une machine est accessible (sinon la raison via le code d'erreur ICMP), mesurer la latence ; souvent utilisé pour alerter quand une machine n'est plus joignable.
- MRTG : réalisé en Perl et C ; surveille la charge des liens réseaux ; génère des pages HTML avec des images PNG (état en temps réel). Un script Perl récupère les données via SNMP et les envoie à un programme C qui les stocke et génère les graphiques ; étendu à toute variable SNMP, voire à des scripts pour données non SNMP.
- RRDTOOL : même auteur que MRTG, évolution ; gestion du stockage revue (technique « Round Robin » -> Round Robin Database TOOL) ; graphiques améliorés, interfaçage modulaire ; incontournable, utilisé dans quasiment tous les logiciels de supervision open-source.
- tcpdump / Wireshark (capture de paquets, détection d'usages frauduleux) ; Iperf (audit du réseau).
Solutions complètes : « console d'administration globale » ; passage à l'échelle (vue globale de centaines de machines puis zoom).
- NetMRG (2001) : historiques et auto-scroll, templates, gestion des jours de travail. Composants : moteur C++ multithreadé (récolte via scripts/SNMP/MySQL), RRDTOOL, base MySQL (config), interface PHP. « Device Tree » : Group -> Device -> Sub device -> Monitors ; « events » en cas de problème.
- Cacti : basé sur RRDTOOL, interface la plus complète ; base MySQL ; moteur de récolte en C (Cactid, Threads POSIX) si besoin de performances, sinon moteur PHP. Interface : « Console » (config) et « Graphs » (affichage) avec trois modes : Tree mode (arbre par groupes), List mode (liste des graphiques d'une machine), Preview mode (graphiques affichés directement).
- Zabbix (2001 ; entreprise Zabbix SIA en 2005) : acquisition des données via SNMP, via test de service (rien à installer, tests limités à des pings ou des protocoles SMTP/HTTP), ou via l'agent Zabbix local (originalité : toute info sans SNMP). Composants : serveur (cœur : centralise par trapping ou polling, configuration, alerte), proxy (optionnel, bufférise pour alléger le serveur), agent (collecte les données locales), interface Web (PHP). Tout en C sauf l'interface Web. Interface en 5 parties : Monitoring, Inventory, Report, Configuration, Administration.
- Nagios : successeur de NetSaint ; le logiciel libre le plus connu. Historique : 1999 NetSaint (Ethan Galstad), 2002 renommé Nagios, 2004 v1.2, 2006 v2.0, 2008 v3.0. Architecture modulaire : moteur en C (ordonnancement), interface Web via CGI, greffons (plugins, plus de 1200). Interface : monitoring (vue globale, précise, carte, problèmes, 3D), reporting, configuration.
  * Plugin = script/programme accomplissant une tâche et une seule ; renvoie un code retour (0 = OK, 1 = WARNING, 2 = CRITICAL, 3 = UNKNOWN) et un petit texte explicatif sur la sortie standard.
  * NRPE (Nagios Remote Plugin Executor) : Nagios initie la vérification (polling) ; NRPE reçoit la demande, exécute, renvoie le résultat. NSCA (Nagios Service Check Acceptor) : vérification planifiée et exécutée en local (trapping), résultat envoyé à Nagios ; inverse le sens des connexions (utile avec des pare-feu en diode). check_by_ssh (comptes non privilégiés, implications de sécurité) ; NSClient / NRPE_NT pour Windows.
  * Fichiers de config dans /etc/nagios ; structure define { param value } (pas d'espace dans les valeurs) ; test de cohérence : nagios -v nagios.cfg. Vérifications le plus souvent actives, parfois passives.
- Centréon (2003, Français, ex-Oréon, repris par Merethis) : évolution de Nagios (interface et fonctionnalités), compatible avec le moteur Nagios.
- Shinken : refonte complète du cœur de Nagios en Python ; architecture plus souple, conçue pour les architectures distribuées ; ~5x plus de performances que Nagios classique ; compatible nagios, nrpe et certains plugins ; supervision à distance via SSH ou tunnel SSL ; gestion des dépendances réseau et logiques ; supervision active et passive ; noms en UTF-8 ; plugins en shell, C++, Perl, Python, Ruby.
- Icinga : fork open-source de Nagios ; visualisation via rapports ; modulaire, interfaces web ou mobiles ; environnements complexes, multi-sites.
Solutions payantes :
- MOM et SCOM (Microsoft) : supervision d'ordinateurs interconnectés (Active Directory, SQL Server, Exchange, SCOM lui-même). Un agent installé sur la machine scrute plusieurs sources (journal d'événements, compteurs de performance, codes de retour) et envoie les infos pertinentes au serveur, qui conserve un historique et déclenche des alertes ; règles selon le contexte : notification (courriel, pager), ticket d'incident, action (script). Management Packs = ensembles de règles et d'informations pour superviser une application spécifique ; SCOM corrige la complexité reprochée à MOM.
- ITM (IBM Tivoli Monitoring) : logiciel de supervision du framework Tivoli d'IBM ; surveille OS, réseau, applications, matériel ; alertes vers une console (Tivoli Enterprise Console) ; version 6.1 basée sur Omegamon de Candle (racheté par IBM).
- BMC Patrol : un des plus anciens logiciels de supervision, pionnier ; multi-plateforme (AIX, HP-UX, Solaris, tous les environnements Windows) ; dénominations telles que « Performance Manager ».
